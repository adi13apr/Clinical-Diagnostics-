## Run notes

**Provider change: Gemini → Groq.** The pilot ran on `gemini-3.8-flash` for both reports and judge. Its free tier allows **20 requests/day per model**: the daily quota (429 `GenerateRequestsPerDayPerProjectPerModel-FreeTier`) stopped the pilot after 2 of 36 cases. A full run is about 108 requests, which would take about 6 days. This run uses Groq's free tier instead: 1000 requests/day and 8000 tokens/min per model (from the `x-ratelimit-*` headers), plus 200k tokens/day (from the docs). That fits a full run in one sitting.
- Reports are written by `openai/gpt-oss-120b` (Production).
- The judge is `qwen/qwen3.8-27b`, a different model family from the report writer, chosen to avoid the self-preference of Gemini judging Gemini. It is a Groq **Preview** model, which Groq describes as "for evaluation purposes only".
- The 2 Gemini pilot results were discarded and are not part of this run or the baseline.

**Ungrounded caveat, fixed before this run.** The pilot judge scored faithfulness 4/5 on `c01` because the report's limitation "evaluated on two public datasets where each disease came from a different source" was not in any tool output. The agent's system prompt *required* that sentence, so the judge was right that it was ungrounded. Fix: the caveat now lives in a tool output (`get_condition_info` → `model_limitations`, from `agent/condition_info.json`), and the system prompt now says limitations must come from that tool. Result: 36/36 reports include a `model_limitations` item verbatim.

**Other changes made while moving to Groq (all before this run):**
- `gpt-oss-120b` can't make parallel tool calls, so each report takes 3 tool turns plus the answer (4 calls, about 4.6k input tokens).
- One smoke-test case failed with Groq `400 tool_use_failed` on the answer turn. Two fixes followed: the answer turn is now sent with tool calls forbidden (`tool_choice: "none"`), and a model-side API error gets one retry before the template fallback. This run had no rejections or fallbacks.
- `qwen/qwen3.8-27b` has an undocumented **1000 output-tokens/min** limit on this account, found from a 429 "Request too large … (OTPM)". With reasoning on, a judgement used about 1.2k output tokens. The judge therefore runs in instruct mode (`reasoning_effort: none`, `max_completion_tokens: 600`, about 170 output tokens), and the rate limiter enforces OTPM.
- At about 58 s per report, latency here is mostly client-side pacing under the 8k tokens/min limit, not model speed.

**How to read these scores:**
- The judge is near the ceiling: means 4.78–4.94, no score below 4. It is also somewhat noisy; for example, `c17` got faithfulness 4 with the reason "all claims … are directly supported". Human scoring (below) shows it agrees on good reports but missed the one bad one.
- The rubric measures faithfulness to the tool outputs, not clinical correctness. Confidently wrong predictions still score 5/5. For example, `c01` is a Normal X-ray called Pneumonia at 99.97%, and its report correctly says "very high confidence". 13 of the 24 model errors are confident (not referred), so no report-level check can catch them.

**Human validation (2026-10-20).** The project owner scored 15 reports blind with the same rubric. Agreement with the judge looks high (81.7% exact, 96.7% within 1 point), but both raters gave almost every report 5/5, so it says little about catching problems. The owner marked down exactly one report, `c32` (3/4/3/3): it says "No immediate referral is required" for a 99.99% Pneumonia result. The judge gave that report 5/5/5/4 and called the wording appropriate. **Conclusion: the judge confirms good reports but missed the one bad report a human caught.** A deterministic check, `abnormal_result_not_dismissed`, now flags "no referral / no action / no follow-up needed" wording on Pneumonia or TB predictions. Normal predictions are exempt, matching the owner's scores. It flags only `c32` in this run (12/13).
